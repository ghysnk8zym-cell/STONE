# ADR-004: Internationalisation and locale routing

**Status:** Accepted (owner approved written ADR 2026-10-13)
**Date:** 2026-10-13
**Deciders:** Project owner (approval), lead engineer (Claude)

## Context

- Locales: ru (default) and en. All user-facing strings live in `messages/ru.json` and `messages/en.json`; no hard-coded text.
- Public pages, auth pages, the account and the admin panel must work in both locales, including redirects behind auth.
- The Figma design is in English; Russian copy is drafted by Claude and reviewed by the owner.
- The language switch is a **button** (owner, 2026-10-13). Figma contains no language switcher, so it is built from the incumbent Nav/Pill component and approved visually in Phase 2.
- Must run on Workers (OpenNext, `middleware.ts`) and on Node/Vercel unchanged.

## Decision

Use **next-intl 4.x** with:

- `locales: ["ru", "en"]`, `defaultLocale: "ru"`, `localePrefix: "always"` (`/ru/…`, `/en/…`);
- `localeDetection: false` — `/` always redirects to `/ru`; a manual switch is remembered in the `NEXT_LOCALE` cookie;
- identical slugs in both locales (`/ru/catalog/black-marble`, `/en/catalog/black-marble`);
- a single `middleware.ts` composing next-intl first and the optimistic auth cookie check second; matcher excludes `/api`, `/_next` and static files;
- namespaced messages (`common`, `nav`, `footer`, `home`, `catalog`, `product`, `calculator`, `account`, `admin`, `auth`) typed through next-intl `AppConfig`;
- `react/jsx-no-literals` ESLint rule plus a key-parity test (identical keys, no empty values);
- product names and descriptions stored as data in `product_translation`, not in messages;
- numbers and prices through `format.number` (USD), units (m²) from messages; the placeholder price is labelled as illustrative;
- `<html lang>` per locale; `generateStaticParams` + `setRequestLocale` for static public pages.

## Options Considered

### Option A: next-intl (chosen)

| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Cost | Free, small runtime |
| Scalability | Good |
| Team familiarity | High; de facto standard for App Router |

**Pros:** Server Component support; typed keys; middleware for routing; ICU formatting.
**Cons:** middleware composition with auth must be written carefully.

### Option B: Hand-rolled dictionaries (Next.js docs pattern)

**Pros:** no dependency. **Cons:** no ICU plurals/formatting, typed keys and routing helpers must be built by hand. Rejected.

### Option C: i18next / react-i18next

**Pros:** large ecosystem. **Cons:** client-oriented, more setup for RSC. Rejected.

## Trade-off Analysis

next-intl gives typed keys, server rendering and routing with minimal code; its only cost is careful middleware composition, which is needed anyway for auth redirects. Always-prefixed URLs make locale explicit in every test and preview link.

## Consequences

- Easier: locale is visible in every URL; tests can target `/ru` and `/en` directly.
- Harder: Russian copy must be maintained for every new string (enforced by the parity test).
- Revisit: localised pathnames and `hreflang` when the site leaves `noindex`.

## New dependencies

`next-intl` 4.x.
